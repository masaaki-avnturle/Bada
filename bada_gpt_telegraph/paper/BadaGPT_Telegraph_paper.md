## 要旨

本稿は、利用者が思い描いたアプリケーションを自然言語で依頼すると、その**依頼の全体**を捉えてアプリケーションを生成し、検証し、生成過程を論文にまとめ、Android (APK)・Windows 10/11・Linux 向けに配布できる形にするシステム「BadaGPT電信」を報告する。BadaGPT電信は、Bada 言語で駆動される通信アプリ「BADA グラビトン電信」の電信エンジン (Bada インタプリタ、ガンマ・ベータ関数による多様体不変量、Jones 多項式、FSK 音響モデム) を受け継ぎ、その上に「全体把握 → 設計 → 生成 → 検証 → 論文」のパイプラインを載せたものである。

中心となる考え方は、依頼文を節に分け、**すべての節**を仕様のいずれかの要素へ対応付け、対応付けられなかった節を捨てずに成果物と論文の双方へ明記することである。これを「節の網羅率」として定量化した。14 種のアプリ部品を組み合わせて依存ゼロの単一 HTML アプリを生成し、構文・オフライン性・依頼部品の実装などを機械的に検証する。

評価では、規則の開発に用いた 24 件の依頼でモジュール選択 F1 100%、規則の修正を終えた後に書いた**未見の 10 件**で F1 81.5%・完全一致率 70% を得た。未見の誤りの事例でも網羅率は 100% であり、網羅率は「取りこぼしがないこと」を示すが「正しく解釈したこと」は示さないことを確認した。生成した全 34 件のアプリは静的検証に合格し、実ブラウザで 7 件の依頼から生成したアプリの全部品を操作して実行時エラー 0 件であった。

**キーワード**: 要求の全体把握, 節網羅率, アプリケーション自動生成, 自己完結 HTML, クロスプラットフォーム配布, Bada 言語, FSK 音響通信

## 1. 序論

### 1.1 背景

Bada は、量子的な演算子 (左作用 `<-`・多様体積分 `-<`・右量子作用 `>-`) と名前空間命令を持つプログラミング言語であり、本リポジトリではこれを用いた多数のアプリケーションが作られてきた。そのひとつ「BADA グラビトン電信」は、宛先とメッセージを Bada プログラム `telegraph.bada` で符号化し、ガンマ関数の大域的部分積分多様体と Jones 多項式の量子テレポーテーションという思考実験を可視化しながら送信し、さらに音声帯域の FSK 変調によってアプリとスマートフォンの間で**実際に**文字データを送受信する。

一方、BadaGPT 系列 (BadaGPT道場、BadaGPT改) では、対話型 AI がアプリケーションを作るときの技法を Bada の上で扱ってきた。本研究はこの二つを統合し、「電信で送られた依頼 (思考入力) を受け取った BadaGPT が、依頼の全体を捉えてアプリケーションを錬成する」システムを構成する。

### 1.2 課題

利用者が頭の中のアプリケーションを言葉にすると、その文章には機能、扱うデータ、項目、並べ替えや検索といった操作、配色、利用する端末などの要求が一文の中に混在する。生成系がこのうち目立つ部分だけを拾い、残りを黙って捨てると、利用者は「言ったのに作られていない」部分を成果物の中から探すことになる。生成系が**何を作り、何を作らなかったか**が見えないことが問題である。

### 1.3 本研究の貢献

1. 依頼文の全節を仕様要素へ対応付け、未解釈の節を成果物と論文に保存する「全体把握」の手続きと、その網羅率の定義 (第 4 章)。
2. 互いに独立した 14 種の実行時部品を組み合わせて依存ゼロの単一 HTML アプリを生成し、機械的に検証する生成器 (第 5 章)。
3. 生成のたびに要求・設計・実装・検証を論文の体裁で書き出し、APK / Windows / Linux のビルド一式とともに配布する仕組み (第 6 章)。
4. 開発用と未見用の二つの依頼集合による定量評価と、実ブラウザ・実パッケージでの動作検証 (第 7 章)。

## 2. 関連する取り組み

**BADA グラビトン電信** (`bada_telegraph/`) — Bada インタプリタ (`set / <- / -< / >- / Omega::push / print / Tele::`)、シャノンエントロピー H とベータ関数による不変量 Ξ = β(H+1, M+1)/log(N+2)、Kauffman 括弧による (2,n) トーラス結び目の Jones 多項式、モールス符号、FSK 音響モデムを持つ。本研究はこれらをそのまま電信層として用いる。

**BadaGPT道場** (`bada_gpt_dojo/`) — トークン化・自己注意・次トークン予測・意図解析・計画と生成・検証と自己修正の 7 つの技を教えるアプリ。意図解析とアプリ錬成を持つが、依頼文のどの部分を何に使ったかは記録しない。

**BadaGPT改** (`bada_gpt_kai/`) — 文章・音声・スケッチ・写真から Claude を用いて APK / EXE 用プロジェクトや PDF を生成する。生成の主体は大規模言語モデルである。

**要求工学におけるトレーサビリティ** — 要求と設計・実装の対応を追跡可能にするという考え方は古くからある。本研究の網羅率は、これを依頼文の節という細かい単位で、生成のたびに自動で行うものと位置付けられる。

## 3. システム構成

### 3.1 パイプライン

BadaGPT電信の処理は、Bada プログラム `badagpt.bada` の実行として表される。

```
set entropy   = H            # 依頼文のシャノンエントロピー (送信時に注入)
set crossings = n            # Jones ブレイドの交差数 (送信時に注入)
line <- "thought request telegraph"
line -< 1.0
line >- line
Omega::push line as thought_node
Tele::encode                 # モールス + エントロピー符号化
Tele::knot crossings         # Jones 多項式で量子チャンネルの結び目
Tele::teleport               # 量子テレポーテーション (思考実験)
Tele::graviton               # グラビトン → 電磁波 搬送波 (思考実験)
Tele::send                   # BadaGPT へ配信
GPT::comprehend              # 全体把握
GPT::plan                    # 設計
GPT::generate                # 生成
GPT::verify                  # 検証
GPT::paper                   # 論文
```

インタプリタは `Tele::` と `GPT::` の名前空間命令を受け取るたびに画面の対応する段を駆動する。`Tele::` 段の数値は山口フレームワークに基づく思考実験の可視化であり、生成結果の正しさには用いない。`GPT::` 段が本研究の主題である。

### 3.2 思考入力

本稿でいう「思考入力」とは、利用者が思い描いたアプリケーションを (a) 文章で書く、(b) 音声認識で話す (対応環境のみ)、(c) 別の端末から FSK 音で電信する、のいずれかで与えた依頼文を指す。脳の信号を読み取る機能はない。

(c) の FSK 電信は、space 1000 Hz / mark 1600 Hz・100 baud の UART 型フレーム (プリアンブル、SOF 0x7E、2 バイト長、UTF-8 本文、チェックサム) で、Goertzel 法により復調する。スマートフォンで書いた依頼をパソコンのアプリへ音で送ることができ、電話のスピーカー越しでも届く。

## 4. 全体把握

### 4.1 節への分割

依頼文を句点・感嘆符・疑問符・改行で文に分け、さらに読点で節に分ける。ただし項目の列挙を含む文 (「項目はタイトル、著者、読了日」「日付、体重、運動時間、メモ」) は読点で切らずに 1 節として保つ。列挙文の判定は、(i)「項目・フィールド・カラム」等の語を含む、(ii) Rails 形式 `name:type` を含む、(iii) 区切りが 2 個以上で「を/の + 記録・管理・登録…」で終わる、(iv) 区切りが 2 個以上で各要素が短い名詞だけからなる、のいずれかとした。

### 4.2 仕様要素への対応付け

各節を次の規則に照合する。

| 仕様要素 | 規則の例 |
|---|---|
| モジュール (14 種) | 「家計簿・支出・収入」→ 家計簿、「タイマー・ポモドーロ」→ タイマー、「量子・ベル状態」→ 量子回路 など |
| 記録対象 | 「X を管理/記録/登録」「X の Y 記録」「X 管理」の X (末尾の漢字・カタカナ・英数字の連続) |
| 項目と型 | 列挙文の各要素。「日・期限」→ 日付、「評価・点数」→ 評価 (1–5)、「金額・数量」→ 数値、「メモ・感想」→ 長文 |
| 機能 | 検索・並べ替え・CSV 書き出し・グラフ・音・印刷 |
| 見た目 | ダーク / ライト、9 色のアクセント色 |
| 対象環境 | スマホ・APK → Android、Windows・パソコン → Windows、Linux・Ubuntu → Linux |
| 題名・目的 | 「」で囲まれた名前、「〜したい」「〜のため」の節 |
| 作成依頼の意図 | 「作って」「欲しい」「お願い」などの短い節 |

記録対象が既存モジュールを指す場合 (「タスクを管理」→ ToDo、「支出を記録」→ 家計簿) は、汎用の記録モジュールを作らずにそのモジュールへ回す。題名の「」の中の語や項目の列挙の語でモジュールを呼ばないよう、それらを除いた本文でモジュールを判定する。

### 4.3 網羅率と、捨てないこと

少なくとも一つの仕様要素に対応した節を「網羅された節」とし、

> 網羅率 = 網羅された節の数 / 全節の数

と定義する。網羅されなかった節は**未解釈の節**として、(1) 生成アプリの「この依頼について」画面に要望メモとして、(2) 論文の考察に原文のまま、(3) Claude を使う場合はプロンプトに `UNRESOLVED` として、必ず残す。依頼に明示されなかった点 (項目が無い、対象環境の指定が無い等) を補った場合は、その**仮定**も同じ三箇所に記す。

## 5. 生成と検証

### 5.1 実行時部品

| 部品 | 主な機能 |
|---|---|
| 記録・管理 | 任意の項目と型による登録・編集・削除・一覧、検索、並べ替え、CSV / JSON、グラフ |
| ToDo | 期限・優先度、完了、絞り込み、進捗バー |
| メモ | 一覧と本文、自動保存、検索、テキスト書き出し |
| 家計簿 | 収入 / 支出・分類・金額、月ごとの集計と分類別グラフ、CSV |
| タイマー | ストップウォッチ (ラップ)、カウントダウン、ポモドーロ、アラーム音 |
| 電卓 | `eval` を使わない再帰下降構文解析、履歴 |
| カウンター | 複数のカウンター |
| クイズ | 単語カードの追加、シャッフル出題、採点 |
| お絵かき | ペン / 消しゴム、色・太さ、元に戻す、PNG 保存 |
| 単位変換 | 長さ・重さ・面積・温度 |
| 抽選 | サイコロ、コイン、くじ引き |
| 習慣 | 直近 14 日の記録と連続日数 |
| 電信 | モールス符号化・復号・打電音 |
| 量子回路 | 2 qubit 状態ベクトル、H / X / Z / CNOT、ベル状態、1000 回測定の分布 |

各部品は生成器のソースの中に**本物の JavaScript 関数**として書かれており、`Function.prototype.toString` で文字列化して生成アプリへ埋め込む。そのため部品のコードは生成器自身の構文検査とテストの対象になる。設定値は `<` を `<` に置き換えた JSON として埋め込み、利用者の文字列で `script` 要素が途切れないようにした。データは端末内 (localStorage) にのみ保存し、ネットワーク通信は行わない。

### 5.2 検証

生成のたびに次を機械的に検査する: HTML 骨格、JavaScript 構文、外部読み込みの有無 (オフライン性)、依頼されたモジュールの実装、項目 (データモデル) の実装、題名の反映、網羅率 (50% 以上)、サイズ。さらに画面上では生成アプリをサンドボックス化した iframe で実際に起動し、読み込み中の実行時エラーを親画面へ通知させて記録する。

### 5.3 Claude による生成 (任意)

API キーが設定されている場合、全体把握の結果 (未解釈の節を含む) と原文を Claude に渡し、単一 HTML の生成を依頼する。既定のモデルは Claude Opus 5.5、思考は adaptive、拒否時は既定の代替モデルへ回す。返った HTML は同じ検証にかけ、不合格なら内蔵エンジンの結果を用いる。キーが無ければすべてオフラインで動作する。

## 6. 論文の自動執筆と配布

`GPT::paper` は、生成ごとに次の章立ての論文を Markdown で書き出す: 要旨、序論 (依頼の原文)、方法 (電信指標・全体把握・生成と検証)、結果 (節ごとの対応表、モジュールと根拠、データモデル、実装の構成、検証結果)、考察 (仮定、未解釈の節、限界)、結論、参考文献。数値はすべて実際の解析・生成・検証の結果から埋める。

この論文は画面で表示でき、Markdown または PDF として保存できる。PDF は日本語を端末のフォントで A4 の画像ページに描き、自前の PDF 書き出し器で埋め込む。

さらに「ビルド一式」として、生成アプリ・論文・Electron 設定・Cordova 設定・GitHub Actions ワークフローを ZIP にまとめる。この ZIP をリポジトリに置いて実行すれば、**生成したアプリそのもの**が Android APK・Windows EXE・Linux AppImage / deb になる。BadaGPT電信自身も同じ方式で 3 種のプラットフォームへビルドし、GitHub Release に添付する。

## 6.5 拡張：サイレント・トーク (非言語思考入力)

言葉を介さずに依頼を与える拡張を加えた。中心となる入力は、利用者が頭に**思い描いたもの**を、文字や絵文字を選ぶのではなく**連続した動き** (ジェスチャー) で面になぞることである。その動きの速さ・広がり (経路長)・向き (8 方位ヒストグラム)・曲がり (角度変化の累積)・リズム (ストローク間隔の分散)・重心を固定の規則で特徴量にし、そこから非言語のアトム列を導く。重心の 3×3 領域が主モジュールを、経路長が文章の分量を、曲がりが気分と配色を、重心の高さが明暗を、主な向きが機能を決めるというように、動きの何がどの意味になったかを「読み取った内容」として利用者にそのまま示す。細かく補うために**無言のグリフ** (感情・領域・対象・動作・分量・環境の 33 アトム) も足せる。

この非言語の列を、固定の重みを持つ小さな**トランスフォーマー** (埋め込み 16 次元・自己注意 2 層・4 頭・位置エンコードつき) が、言語化されていない潜在表現 (latent) に変換する。重みは固定の疑似乱数で初期化され学習は行わないため、同じ動きは必ず同じ latent を与える (決定的)。自己注意の各行は確率分布になる (行和 = 1、実測誤差 2×10⁻¹⁶)。

latent からは四つを決定的に復号する: (a) **本と同じ分量まで展開できる文章** (分量アトムに応じて素描〜約 96,000 字。latent と疑似乱数で駆動するテンプレート展開)、(b) **イメージ** (latent から生成する SVG)、(c) **Bada 言語のプログラム** `silent.bada` (`BadaInterp` が構文エラーなく実行できる)、(d) 以降の全体把握へ渡す**依頼文**。

正直な範囲として、これは利用者が**自分で描いた動き**を固定の規則で言葉にするものであり、脳の信号は読み取らない。トランスフォーマーは学習済みの大規模言語モデルではなく、文章は意味のある新規の内容ではなく latent に駆動された展開である。単体テストで、決定性・注意行和・分量の増加・Bada プログラムの実行可能性・下流の全体把握との接続を検証した (第 7.1 節)。

## 6.6 拡張：ソースコード化

文章化された思いを、HTML アプリだけでなく**人が読めて実行できるソースコード**に変換する拡張を加えた。全体把握した仕様 (モジュール・対象・項目と型・機能) を、生成器がソースコードに写す。

記録・管理 (records) を主とする仕様は、**実際に動く CLI アプリ**として生成する。Python (`python3 app.py`) と Node.js (`node app.js`) のいずれも、項目ごとの入力・一覧・検索・並べ替え・CSV / JSON 書き出しを持ち、データを端末内のファイルに保存する (依存ライブラリなし)。それ以外のモジュール (タイマー・お絵かき等) は言語とデバイスに依存するため、仕様をデータとして埋め込んだ**構文的に正しい雛形**として生成し、拡張点を TODO で示す。完成した動作は HTML アプリ版が担う。Bada はいずれの場合も Bada 言語のプログラム (`BadaInterp` で実行可能) を生成する。全言語をまとめて ZIP で保存できる。

生成されるコードは生成器の中でテンプレートとして組み立てられ、利用者の項目名などは文字列として安全に埋め込む。単体テスト (第 7.1 節) で、生成した Python を `py_compile`、Node を `node --check` にかけて構文を確かめ、さらに records の Python / Node を実際に実行して「追加 → 一覧 → CSV 書き出し」が動き、JSON と CSV がファイルに書かれることを確認した。

## 6.7 拡張：体のサイン (自己バイオフィードバック) と、行わないこと

利用者が**自分の**指先をカメラに当てて得る脈波 (PPG) から心拍数と心拍変動 (RMSSD) を、マイクの音量包絡から呼吸数を推定し、落ち着き指数にまとめる (BadaGPT改の信号処理を移植。合成信号で心拍 55 / 72 / 110 bpm を誤差 2 bpm 以内、呼吸 6 / 12 / 20 回/分を 0.5 以内で推定することを単体テストで確認)。結果はサイレント・トークの latent に**気分のヒント (静か / 軽やか / 勢い の tone アトム) としてだけ**加わる。体の信号がアプリのモジュール・対象・項目を決めることはなく、依頼文のモジュールと対象が変わらないことを単体テストの不変条件とした。

**行わないこと (明記).** 本システムは、赤外線カメラや温度計で他人の体内情報や思考を読み取る機能を持たず、またそれを主張しない。皮膚温や赤外線画像から思考の内容や言語を推定することは科学的にできない。ガンマ関数の大域的部分積分多様体と Jones 多項式は本システムでは思考実験の可視化であり、センサーではない。体のサインは本人が自分を測る自己計測 (同意が前提) に限る。

## 6.8 拡張：自動コンパイル (思考入力から exe / apk まで)

思考入力 → 文章 → 仕様 → ソースコード まで来た成果物を、exe / apk に**自動でコンパイル**する段を加えた。WebView や Electron の中では Gradle や electron-builder を実行できないため、実際に成立する仕組みとして次を採った: (1) 生成した一式 (アプリ本体・Electron / Cordova 設定・3 言語のソースコード・論文・ビルド用 GitHub Actions ワークフロー) を、利用者自身のトークンで利用者の GitHub リポジトリへ **Git Data API による 1 コミット** (blobs → tree → commit → ref) でプッシュする (リポジトリが無ければ作成)。(2) プッシュが `apps/<slug>/**` を監視するワークフローを起動し、Android APK・Windows EXE・Linux AppImage/deb をビルドして、Actions アーティファクト (個別 + 一式) と Release `<slug>-latest` (ログイン不要の直リンク) に置く。(3) BadaGPT は同じ commit の実行を探してポーリングし、ジョブの進行・成否・アーティファクト・Release 資産を表示する。

この層は fetch と sleep を注入できる純関数群として書き、偽の GitHub API に対する呼び出し順序 (リポジトリ作成 → ブランチ → blobs × ファイル数 → tree → commit → ref 更新)、ペイロード (base_tree・parents)、トークンがログや URL に出ないこと、同一 commit の他ワークフローを除外して自分の実行を選ぶことを単体テストで検証した。生成するワークフローは YAML として解析し、3 つのビルドジョブと publish、push (paths) と手動起動を持つことを確かめた。実ブラウザでは API をモックして、錬成 → プッシュ → 起動待ち → ビルド中 → 完了 (Release 直リンク 2 件・アーティファクト 2 件) までの画面遷移を通した。端末内で行うのは HTML 検証・Bada 実行・Node 構文の事前チェックまでであり、本当のコンパイルは利用者のリポジトリの Actions 上で利用者の権限で行われる。

## 6.9 拡張：思考だけで (脳波 BCI による選択)

声を出さず、絵も描かず、文字も打たずに入力する要望に対し、現在の技術で正直に成立する形として**ブレイン・コンピュータ・インタフェース (BCI)** を実装した。利用者が自分の頭に付けた脳波計 (EEG) の信号から、(a) **集中度** = β (13–30 Hz) / (α 8–12 Hz + θ 4–7 Hz) のバンドパワー比、(b) **SSVEP** (定常状態視覚誘発電位) = 見つめている点滅刺激の周波数成分、を推定し、BadaGPT が順に提示する選択肢を**注意を向けるだけで選ぶ**。選択は段階 (何のアプリ・対象・機能・調子・分量・環境) ごとに行い、選ばれた非言語アトム列をサイレント・トークの復号 (文章・依頼文・Bada) に渡して、以降のアプリ生成・ソースコード化・自動コンパイルへ接続する。

集中による選択は、選択肢を 3 秒ごとに移すスキャンの中で、集中度がしきい値を超えて 1.2 秒続いた選択肢を確定する (dwell 選択)。SSVEP による選択は、選択肢を 60 Hz 描画の約数 6 / 7.5 / 8.57 / 12 / 15 Hz で点滅させ、各候補周波数のパワーを Goertzel で求め、5–30 Hz のスペクトル (候補近傍を除く) の**中央値を雑音床**として SNR を取り、最大候補が雑音床の 12 倍以上かつ次点の 2 倍以上のときだけ採用する。10 Hz を候補から外したのは背景の α 律動と、20 Hz を外したのは集中時の β と混同するためで、設計の過程で合成信号がこの両方の誤検出を実際に示した。機器は Muse (Web Bluetooth、12 ビット × 12 サンプルの通知を復号) と OpenBCI Cyton (Web Serial、33 バイト枠の 24 ビット 2 の補数を復号) に対応し、機器が無いときは合成信号のデモ (シミュレーションであることを明示) で仕組みを示す。

合成脳波 (α 9.6–10.4 Hz・β 14–26 Hz の広帯域・θ・雑音) による検証では、5 周波数 × 20 乱数系列 × 安静/集中の 200 件で見逃し 0 (採用時の最小 SNR 129)、刺激なし 40 件で誤検出 0 (背景の最大 SNR 9.9) であった。集中度は安静 0.27 / 集中 0.94 で分離した。パケット復号は既知の生値を詰めた往復で検証した。**限界と正直な範囲.** 脳波計が読むのは脳の**状態**であり、思考の内容や言語は読み取れない。利用者は提示された選択肢から選ぶのであって、自由な文を思考から取り出すのではない。実機の脳波は個人差・電極の接触・まばたきの影響が大きく、しきい値の調整が必要である。他人の脳波を読む用途ではなく、本人が同意の上で自分の機器を使う。

## 6.10 拡張：Ω-Telephacy (無音の口形による音声認識) と ChatGPT 版チャット

声を出さずに語を伝える要望に対し、本リポジトリの `bada_silent_vim/silenttalk` (Python) を移植して**無音の口形 (viseme) 認識**を実装した。カメラ映像の口付近 ROI で、口腔の暗い領域の外接矩形から縦の開き (aperture)・横の開き (spread)・暗部率 (energy) を測り、フレームを C (閉じ) / A / I / U / O / E に分類する。しきい値は ROI 輝度の中央値から適応的に決め、閉じた口と大きく開けた口の 2 点較正で 0..1 に正規化する。連続する同じ口形を縮約し (CTC 風)、閉じで発話に区切り、縮約した口形語 (例 AI) を辞書で BadaGPT の非言語アトムまたは命令 (作って・やり直し・戻す) に引く。口形から 7 段階の共鳴スケール (do〜si) を再構成し、Γ多様体 × Jones 多項式の「熱エネルギー経路」|V_{T(2,n)}(e^{2πi/5})|, n = 3 + 2·round(7·feat) で語の重みを可視化する。Jones の複素評価は Kauffman 括弧から求めた V(A) を A = t^{−1/4} で評価し、三葉結び目の閉形式 t + t³ − t⁴ と一致することを確かめた。語列は既存のトランスフォーマー (6.5 節) で latent に組み立てられ、文章・アプリ・ソースコード・自動コンパイルへ流れる。

併せて、Ω-Telepathy のホバー滞留 (dwell) 選択、Ω-Thermal Trace の疑似サーモ表示 (動きエネルギーの疑似カラーであり実温度ではない)、画像の明るさ・彩度・色相を調子と色のアトムにするイメージ入力を取り入れ、ChatGPT 風の対話面 (BadaGPT チャット) を設けた。チャットは口形・脳波・動き・画像・文字のどの入力でも受け、「作って」の意図で錬成を走らせて結果を返答する。

検証は Python 版の試験と同じ観点で行った: 合成した口形フレームで各 viseme が自分自身に分類されること、辞書の全語 (27 語) が合成フレーム列から往復して復号されること、縮約と区切り、辞書にない列の扱い、適応しきい値の範囲、較正の正規化、共鳴帯の正規化、熱経路の n の範囲、イメージ入力の対応、チャットの意図振り分け。**限界と正直な範囲.** 認識できるのは辞書にある口形語であり、自由な読唇や思考の読み取りではない。実際のカメラでは照明・顔の位置・ひげや化粧の影響を受けるため、較正と枠内への位置合わせが必要である。熱 (温度) は測らない。利用者本人の顔を本人の同意の上で映す。

## 8. 考察と限界

**規則による解析の限界.** 内蔵エンジンは語彙と規則に基づくため、辞書にない新しい種類の機能は 14 部品の組み合わせでしか表せない。未見集合で F1 が 100% から 81.5% に下がったことは、開発集合に合わせて規則を育てると楽観的な値が出ることを示しており、今後も評価には未見の依頼を使い続ける必要がある。誤りの多くは余分な部品を加える方向であり、利用者が「この依頼について」と対応表で気付ける形で現れる。

**Claude との分担.** API キーを設定した場合、規則による全体把握の結果を Claude に渡すことで、辞書にない機能も生成できる。このとき規則側の役割は「どの節をまだ解釈していないか」を明示して取りこぼしを防ぐことに移る。

**電信の物理量.** グラビトン↔電磁波変換と量子テレポーテーションの数値は山口フレームワークに基づく思考実験の可視化であり、物理的な通信を主張するものではない。実際に動作する通信は FSK 音響電信である。

**思考入力.** 本システムは文章・音声・電信で与えた依頼文を扱い、脳の信号は読み取らない。

## 9. 結論

BADA グラビトン電信の電信エンジンの上に、依頼の全節を仕様へ対応付ける全体把握、14 部品による自己完結アプリの生成、機械的な検証、生成過程の論文化、3 プラットフォームへの配布を備えた BadaGPT電信を構成した。未見の依頼で F1 81.5% という結果は規則による解析の限界を示す一方、網羅率と節ごとの対応表は、生成系が何を作り何を作らなかったかを利用者に見えるようにした。未解釈の節と仮定を捨てずに残すという設計は、生成方式 (規則か大規模言語モデルか) によらず有効であると考える。
